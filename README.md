# Лабораторная работа № 5: нормализация данных до 3НФ

Практическая работа на MySQL в Docker: аномалии в плоской таблице «заказы — клиенты — товары — товарная классификация», разложение данных на пять связанных таблиц (клиент проводится по коду заказа, товары классифицируются по коду товара), проверка переноса, резервные копии и журнал SQL-действий.

Выполняется в связке **VS Code — Git Bash — Docker CLI** (контейнер `my-mysql`, пароль root `123`).

## 1. Что нормализуем

Исходная таблица из задания хранит в одной строке шапку заказа, клиента, товар и его классификацию:

| Код заказа | Дата | Код клиента | Имя клиента | Код товара | Название товара | Цена | Код классификации | Имя классификации | Количество |
|---:|:---:|---:|---|---:|---|---:|---:|---|---:|
| 5001 | 2026-03-02 | 101 | Иванов И. И. | 201 | Монитор | 15000 | 301 | Электроника | 3 |
| 5001 | 2026-03-02 | 101 | Иванов И. И. | 202 | Клавиатура | 2500 | 302 | Аксессуары | 5 |
| 5002 | 2026-03-04 | 102 | Петров П. П. | 204 | Ноутбук | 65000 | 301 | Электроника | 2 |
| 5003 | 2026-03-06 | 101 | Иванов И. И. | 203 | Мышь | 1200 | 302 | Аксессуары | 10 |
| 5003 | 2026-03-06 | 101 | Иванов И. И. | 205 | Флешка | 900 | 302 | Аксессуары | 20 |
| 5004 | 2026-03-09 | 103 | Сидорова А. А. | 202 | Клавиатура | 2500 | 302 | Аксессуары | 2 |
| 5004 | 2026-03-09 | 103 | Сидорова А. А. | 204 | Ноутбук | 65000 | 301 | Электроника | 1 |
| 5005 | 2026-03-11 | 102 | Петров П. П. | 201 | Монитор | 15000 | 301 | Электроника | 1 |
| 5005 | 2026-03-11 | 102 | Петров П. П. | 203 | Мышь | 1200 | 302 | Аксессуары | 4 |

Потенциальный ключ строки — `(order_id, product_id)`. Функциональные зависимости:

- `order_id → order_date, customer_id, customer_name` — клиент проводится по коду заказа: один заказ делает ровно один клиент
- `customer_id → customer_name`
- `product_id → product_name, price, class_id` — товары классифицируются по коду товара
- `class_id → class_name`
- `(order_id, product_id) → quantity`

Нарушения нормальной формы:

- **2НФ** — дата и клиент зависят только от `order_id`, товар и классификация — только от `product_id` (частичные зависимости от составного ключа).
- **3НФ** — транзитивные зависимости: `customer_id → customer_name`, `product_id → product_name, price, class_id`, `class_id → class_name`.
- **Аномалии**: исправление имени клиента затрагивает все его строки; новый клиент/товар/классификацию нельзя завести без заказа; удаление единственного заказа клиента стирает и самого клиента.

`orders_bad` намеренно не имеет первичного ключа и ограничений `NOT NULL` — так нагляднее показывать недостатки исходной структуры.

## 2. Схема 3НФ

| Таблица | Первичный ключ | Что хранит |
|---|---|---|
| `customers` | `customer_id` | Код и имя клиента |
| `product_classes` | `class_id` | Код и имя товарной классификации |
| `products` | `product_id` | Товар, цена и **его** классификация |
| `orders` | `order_id` | Дата и **один** клиент заказа |
| `order_items` | `(order_id, product_id)` | Товар и количество в заказе |

В `orders` клиент задаётся внешним ключом на `customers`: `customer_id` — одиночный атрибут шапки заказа, поэтому связь «один код заказа = один клиент» гарантируется структурой. В `products` классификация задаётся внешним ключом на `product_classes` — товар классифицируется по коду товара. Каждый атрибут зависит от ключа своей таблицы, от всего ключа и не транзитивно — схема в 3НФ.

## 5. Демонстрация аномалий

```bash
docker exec -i -e MYSQL_PWD=123 my-mysql mysql -uroot --table --default-character-set=utf8mb4 < sql/02_anomalies.sql
```

- **Обновление:** клиент 101 встречается в 4 строках; исправление имени требует обновить все строки. Частичное обновление даёт противоречие — у одного клиента два имени:

```
+-------------+----------------------------------------+-----+
| customer_id | customer_name                          | cnt |
+-------------+----------------------------------------+-----+
|         101 | Иванов И. И.                           |   2 |
|         102 | Петров П. П.                           |   3 |
|         101 | Иванов Иван Иванович                   |   2 |
|         103 | Сидорова А. А.                         |   2 |
+-------------+----------------------------------------+-----+
```

- **Вставка:** новую классификацию нельзя добавить без товара и заказа — появляется строка-мусор с `NULL`:

```
+----------+------------+-------------+---------------+------------+--------------+-------+----------+--------------+----------+
| order_id | order_date | customer_id | customer_name | product_id | product_name | price | class_id | class_name   | quantity |
+----------+------------+-------------+---------------+------------+--------------+-------+----------+--------------+----------+
|     NULL | NULL       |        NULL | NULL          |       NULL | NULL         |  NULL |      303 | Мебель       |     NULL |
+----------+------------+-------------+---------------+------------+--------------+-------+----------+--------------+----------+
```

- **Удаление:** удаление заказа 5004 стирает и информацию о клиенте 103 «Сидорова А. А.» — оба контрольных запроса возвращают пустое множество (`Empty set`).

Каждая пробная операция выполняется в транзакции и отменяется `ROLLBACK`, поэтому финальная выборка показывает исходные 9 строк без изменений (скриншот `image-1.png`).

## 6. Дамп до нормализации

Лог временно выключается, чтобы служебные запросы `mysqldump` не попали в журнал действий:

```bash
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'OFF';"
docker exec -e MYSQL_PWD=123 my-mysql mysqldump -uroot --set-gtid-purged=OFF --single-transaction orders_norm_lab5 > dump_before.sql
docker exec -e MYSQL_PWD=123 my-mysql mysql -uroot -e "SET GLOBAL general_log = 'ON';"
ls -lh dump_before.sql
```

В `dump_before.sql` — только исходная таблица `orders_bad` с данными.
